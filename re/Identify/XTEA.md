# XTEA

## 算法原理

### 1. 数据拆分

64位（8字节）的明文被平均拆成两个32位的半块：

我们假设`v0`为左半块，`v1`为右半块，如`0x0123456789ABCDEF`被拆成`0x01234567` (左半块 `v0`)和`0x89ABCDEF`(右半块 `v1`)

### 2. 密钥拆分

128位（16字节）的密钥被拆成4个32位子密钥：

`k0, k1, k2, k3`(同上拆分)

但 XTEA 并不是固定使用这 4 个子密钥，而是通过累加器 `sum` 动态选择当前轮要使用哪一个子密钥，这是它比 TEA 更安全的重要原因

### 3. 轮函数与累加器

算法执行 32 轮或 64 轮迭代，引入一个累加器 `sum`，从 0 开始，每轮固定增加一个魔法常数 `delta = 0x9E3779B9`

### 4. 轮运算

每一轮按顺序执行以下两步：

**步骤一：** 用右半块 `v1` 搅动左半块 `v0`

```text
v0 += (((v1 << 4) ^ (v1 >> 5)) + v1) ^ (sum + key[sum & 3])
```

分解来看，这个表达式由两层组成：

- 内层：`((v1 << 4) ^ (v1 >> 5)) + v1` —— 将 v1 左移4位、右移5位后异或，再与 v1 相加（非线性扩散）
- 外层：`... ^ (sum + key[sum & 3])` —— 将内层结果与 `(sum + key[sum & 3])` 异或，其中 `sum & 3` 相当于 `sum % 4`，用于从 4 个子密钥中动态选一个

最后把整个表达式加到 `v0` 上，完成左半块的更新。

**步骤二：** 用更新后的左半块 `v0` 搅动右半块 `v1`

```text
v1 += (((v0 << 4) ^ (v0 >> 5)) + v0) ^ (sum + key[(sum >> 11) & 3])
```

逻辑完全一样，只是换成了用更新后的 `v0` 去更新 `v1`，密钥下标改为 `(sum >> 11) & 3`，再次动态选密钥

最后把整个表达式加到 `v1` 上，完成右半块的更新。

注意：`sum` 在第一步结束后已经加了 `delta`，所以第二步使用的 `sum` 是更新后的值，密钥下标也随之变化

加密模板如下

```c
#include <stdint.h>

#define DELTA 0x9E3779B9

void xtea_encrypt(uint32_t v[2], const uint32_t key[4], unsigned int rounds) {
    uint32_t v0 = v[0], v1 = v[1];
    uint32_t sum = 0;

    for (unsigned int i = 0; i < rounds; i++) {
        v0 += (((v1 << 4) ^ (v1 >> 5)) + v1) ^ (sum + key[sum & 3]);          // 搅拌 v0
        sum += DELTA;                                                        // 更新轮次
        v1 += (((v0 << 4) ^ (v0 >> 5)) + v0) ^ (sum + key[(sum >> 11) & 3]); // 搅拌 v1
    }

    v[0] = v0;
    v[1] = v1;
}
```

### 解密原理

由于 Feistel 网络的可逆性，解密过程完全复用加密代码，只需做几处修改：

- 将 `sum` 的初始值设为 `轮数 × delta`（加密结束时的值）
- 每轮先将 `sum` 减去 `delta`（即逆向累加）
- 轮内运算顺序颠倒：先更新 `v1`，再更新 `v0`（因为加密时最后更新的是 `v1`）

说人话就是模拟结束量，完全反过来一次

学习完以上知识我们可以看到，要逆向 XTEA 我们需要密钥流，密文即可

一般而言，解密脚本如下：

```c
#include <stdio.h>
#include <stdint.h>

#define DELTA 0x9E3779B9

// XTEA 解密函数
// v: 密文数组（8字节，解密后变成明文）
// key: 密钥数组（16字节）
// rounds: 加密时使用的轮数，解密必须保持一致
void xtea_decrypt(uint32_t v[2], const uint32_t key[4], unsigned int rounds) {
    uint32_t v0 = v[0], v1 = v[1];
    uint32_t sum = DELTA * rounds;   // 逆向起始值

    for (unsigned int i = 0; i < rounds; i++) {
        // 解密顺序和加密完全相反：
        // 加密最后一步是更新 v1，所以解密第一步要还原 v1
        v1 -= (((v0 << 4) ^ (v0 >> 5)) + v0) ^ (sum + key[(sum >> 11) & 3]);

        sum -= DELTA;   // 逆向递减

        v0 -= (((v1 << 4) ^ (v1 >> 5)) + v1) ^ (sum + key[sum & 3]);
    }

    v[0] = v0;
    v[1] = v1;
}
```

## TIPS：

**Q1：明文长度不是8字节的整数倍怎么办？**

**A：** XTEA 算法本身不处理填充，它只加密64位整块。如果明文不足8字节，调用者必须在加密之前手动补位。

**PKCS#7填充：** 缺几个字节就补几个 `0x0n`。例如缺3字节就补 `0x03 0x03 0x03`。如果明文刚好8字节，必须额外补满一整块 `0x08 × 8`

**零填充（CTF常见）：** 直接用0x00补满剩余位，逆向时如果看到加密前有memset清零，请考虑零填充

**Q2：为什么我手算的拆分结果和Python跑出来的不一样？**

**A：** 因为x86/x64电脑内存是小端序（低位字节在前）。

例如明文`0x0123456789ABCDEF`，你肉眼看是`01 23 45 67 89 AB CD EF`。但在小端序机器上，uint32_t实际存储是：

`v0`的内存字节：`67 45 23 01`（逻辑值`0x01234567`）

`v1`的内存字节：`EF CD AB 89`（逻辑值`0x89ABCDEF`）

**Q3：写解密脚本怎么处理PKCS#7填充？怎么处理端序问题?**

**A:** 端序问题可以通过查询程序端序，如果是小端序，人肉反过来就行

**PKCS#7 填充移除**

**加密时：** 缺 n 个字节，就在末尾补 n 个 n（把"缺了几个"这个数字，当值填进去）

**解密时：** 看最后一个字节的值（就是那个 n），末尾这 n 个字节肯定全都是 n，直接切掉它们就行

**先验证：** 末尾 n 个字节是否全部等于 n，再进行删除

```c
/**
 * PKCS#7 去填充（严格校验）
 * @param input       填充后的数据
 * @param input_len   填充后的长度
 * @param block_size  块大小
 * @param output_len  输出原始数据长度
 * @return 0 成功，-1 填充非法或参数错误
 */
int pkcs7_unpad(const uint8_t *input, size_t input_len,
                size_t block_size, size_t *output_len)
{
    if (block_size == 0 || block_size > 255)
        return -1;
    if (input == NULL || output_len == NULL)
        return -1;
    if (input_len == 0 || input_len % block_size != 0)//检查输入数据的长度是否是块大小（block_size）的整数倍
        return -1;

    uint8_t pad_len = input[input_len - 1];

    // 填充长度必须在 1 ~ block_size 之间
    if (pad_len < 1 || pad_len > block_size)
        return -1;

    // 检查最后 pad_len 个字节是否都等于 pad_len
    for (size_t i = input_len - pad_len; i < input_len; i++) {
        if (input[i] != pad_len) {
            return -1;  // 填充格式错误
        }
    }

    *output_len = input_len - pad_len;
    return 0;
}
```

**Q_Q3:** 对于一个加密单位也就是8字节，假如是前7字节任意，最后一个字节空的情况和最后一个字节恰是0x1的情况怎么区分，怎么分出是填充还是原始数据？

**A:** 标准 PKCS#7 规定"总是填充"，即使明文长度已经是块大小的整数倍，也会额外补一个完整块

**情况 1：原始 7 字节数据**

```text
原始：     41 42 43 44 45 46 47
填充后：   41 42 43 44 45 46 47 01
```

最后一个字节是 `0x01`，去填充时检查最后 1 个字节等于 `0x01`，合法，去掉 1 字节，得到 7 字节原始数据。

**情况 2：原始 8 字节数据，最后一个字节恰好是 0x01**

```text
原始：     41 42 43 44 45 46 47 01
填充后：   41 42 43 44 45 46 47 01 08 08 08 08 08 08 08 08
```

因为原始长度 8 已经是块大小整数倍，PKCS#7 会补一个完整块，最后一块是 8 个 `0x08`

**Q4：我在 IDA 里看到的是 0x61C88647，不是 0x9E3779B9，是不是认错了？**

**A：** 没认错，这两个是同一个东西。

`0x61C88647` 是 `-0x9E3779B9` 在 32 位整数下的补码表示。很多编译器和逆向工具会把减法优化成加负数，所以解密里的 `sum -= delta` 在 IDA 里常显示成 `sum += 0x61C88647`，加密里也可能写成 `sum -= 0x61C88647`（等价于 `sum += 0x9E3779B9`）。看到 `0x61C88647` 就等于看到了负的 delta，别当成别的常数。

**Q5：如果作者把 XTEA 的 sum += delta 放到了循环末尾，或者把两步更新顺序调换了，解密脚本要调整吗？**

**A：** 要，而且这直接关系到 Feistel 的逆序。

标准加密顺序是：

更新 v0

sum += delta

更新 v1

解密就必须反着来：

恢复 v1（用当前的 sum）

sum -= delta

恢复 v0

如果是把加密顺序改成先更新 v1 再更新 v0，那解密也对应变成先恢复 v0 再恢复 v1。总之解密是加密的完全逆过程，你把加密的每一步倒着写回去就对了，不需要理解每步的数学含义。

**Q6：逆向时怎么区分 TEA 和 XTEA？**

**A：** 看轮函数里密钥是怎么用的，这是两者最直观的区别：

- TEA：固定用 4 个子密钥 `k0, k1, k2, k3`，表达式形如 `((v1 << 4) + k0) ^ (v1 + sum) ^ ((v1 >> 5) + k1)`
- XTEA：用 `key[sum & 3]` 和 `key[(sum >> 11) & 3]` 动态取子密钥，代码里没有独立的 `k0 ~ k3` 变量

只要看到 `key[... & 3]` 这种拿累加器当下标取密钥的形式，基本就是 XTEA

**Q7：XTEA 的轮数怎么定？**

**A：** 原始论文定的是 64 轮，但很多实现（尤其 CTF 题）用的是 32 轮。逆向时别死记一个数，先看循环次数。加密和解密的 `rounds` 必须一致，解密时 `sum` 初值 = `rounds × delta`，轮数对不上会解出乱码
