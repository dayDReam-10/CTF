# 设备指纹及其识别

Android 设备指纹指的是对设备硬件、系统、软件、网络及用户行为等特征进行多维度采集、 汇总和计算后，得到的一个相对独特、稳定的标识，主要用于区分不同的物理设备，识别用户真实环境，防止多开或模拟器滥用等安全、统计或广告场景

目前存在的指纹分为如下几层

● 系统服务 (system_service) 层指纹
● 内核层 (Kernel) 指纹
● 系统属性
● 第三方厂商自带(这个就不展开了)

### Settings.Secure

#### Android ID

 Android ID 的本质是 "某个应用在某个用户下的某个设备上的标识"

它在 `Android` 系统内部 主要是通过设备首次启动或系统初始化时随机生成 然后以明文字符串的形式存储在系统的 `settings.db` 表中 对应 `Settings.Secure` 表中的 `android_id` 字段

五种获取方式

1，标准api调用

```java
String androidId = Settings.Secure.getString(
    context , Settings.Secure.ANDROID_ID);
    //App 进程 → ContentResolver.getString → Binder → system_server 的 SettingsProvider
```

```js
Java.perform(function() {
    // 1 找到类
    var SettingsSecure = Java.use("android.provider.Settings$Secure");

    // 2 定位方法 有重载要指定参数类型
    SettingsSecure.getString.overload(
        "android.content.ContentResolver",
        "java.lang.String"
    ).implementation = function(resolver, name) {

        // 3 打印原始参数
        console.log("getString called, name = " + name);

        // 4 如果读的是 android_id 就返回假值
        if (name === "android_id") {
            console.log("拦截 android_id 返回伪造值");
            return "0000000000000000";
        }

        // 5 其他字段走原始逻辑
        var result = this.getString(resolver, name);
        console.log("原始返回值 = " + result);
        return result;
    };
});
```

2 反射读缓存

```java
// 方式2 反射读 Settings.Secure 的内存缓存 mValues
// 前提 必须先调用过方式1 让缓存被填充 否则 mValues 里没有 android_id

ArrayMap mValues = null;
try {
    // 第一步 反射拿到 Settings.Secure 类里的静态字段 sNameValueCache
    // sNameValueCache 是 Settings.Secure 的静态内部类实例
    // 它负责管缓存 避免每次都走 Binder
    Field sNameValueCache = Settings.Secure.class.getDeclaredField("sNameValueCache");
    sNameValueCache.setAccessible(true);

    // get(null) 取静态字段的值
    // 拿到 sNameValueCache 对象
    Object sLockSettings = sNameValueCache.get(null);

    // 第二步 从 sNameValueCache 对象的类里反射拿 mValues 字段
    // mValues 是一个 ArrayMap 存的就是缓存下来的 key-value
    Field fieldmValues = sLockSettings.getClass().getDeclaredField("mValues");
    fieldmValues.setAccessible(true);

    // 拿到 mValues 这个 ArrayMap
    mValues = (ArrayMap<String,String>) fieldmValues.get(sLockSettings);

    // 第三步 直接从 map 里取 android_id
    // 这就是方式1 之前缓存下来的值
    String android_id = (String)mValues.get("android_id");
    CLog.i(String.format("android_id -> 3333 %s", android_id));
} catch (Throwable e) {
    e.printStackTrace();
}
```

Hook思路

```js

    // 1 拿到 Settings.Secure 类
    var SettingsSecure = Java.use("android.provider.Settings$Secure");

    // 2 反射拿静态字段 sNameValueCache
    var sNameValueCacheField = SettingsSecure.class.getDeclaredField("sNameValueCache");

    // 3 反射拿 sNameValueCache 里的 mValues
    var mValuesField = sNameValueCache.getClass().getDeclaredField("mValues");
    mValuesField.setAccessible(true);
    var mValues = mValuesField.get(sNameValueCache);

    // 4 把 mValues 转成 ArrayMap 类型 然后改值
    var ArrayMap = Java.use("android.util.ArrayMap");
    var map = Java.cast(mValues, ArrayMap);
    map.put("android_id", "0000000000000000");

});
```

方式 1 走 `Binder` 拿值 如果改机方 `Hook` 了 `Settings.Secure.getString` 方式 1 拿到假值

方式 2 读缓存 如果缓存里是真值 方式 2 能发现方式 1 被 `Hook`

方式 3 通过 `ContentResolver.call`间接获取 `Android ID`

```java
// 和方式1 的区别 方式1 走 Settings.Secure.getString 封装
// 方式3 跳过这层封装 直接调 ContentResolver.call

// 第一步 拿到 ContentResolver 管理类
// 和方式1 一样 context.getContentResolver() 返回的不是代理 是管理类
ContentResolver resolver = context.getContentResolver();

// 第二步 构造 Uri
// content:// 是协议头 表示走 ContentProvider 机制
// settings 是 authority 目标 ContentProvider 的名字
// secure 是路径 表示要访问 Settings.Secure 这张表
Uri uri = Uri.parse("content://settings/secure");

// 第三步 调 ContentResolver.call
// 参数1 uri 告诉它要找哪个 ContentProvider
// 参数2 "GET_secure" 是 SettingsProvider 暴露的 call method 名字
// 参数3 "android_id" 是要读的具体 key
// 参数4 new Bundle() 是额外参数 这里为空
Bundle callResult = resolver.call(
    uri,
    "GET_secure",
    "android_id",
    new Bundle()
);

// 第四步 从返回的 Bundle 里取值
// SettingsProvider 把结果放在 key 为 "value" 的位置
String androidIdValue = callResult.getString("value");
CLog.i(String.format("android_id -> 1111 %s", androidIdValue));
```

内部流程

`ContentResolver.call` 收到请求后 做这几件事

```java
// ContentResolver.call 内部简化逻辑
public Bundle call(Uri uri, String method, String arg, Bundle extras) {
    // 1 从 uri 里解析出 authority "settings"
    String authority = uri.getAuthority();

    // 2 根据 authority 找到对应的 IContentProvider 代理
    // 这一步才是真正的跨进程代理 内部字段是 mRemote
    IContentProvider provider = acquireProvider(authority);

    // 3 调代理的 call 方法 这一步真正跨进程
    // 内部构造 Parcel 调 transact
    // Binder 驱动把请求转发到 system_server
    return provider.call(mAttributionSource, authority, method, arg, extras);
}
```


```text

  → 不走 Settings.Secure.getString 那层封装
  → 不查 Settings.Secure 自己的缓存
```

方式5 直接通过 IPC 和服务端通信获取 Android ID

```java
// 手动拿到 IContentProvider 的 Binder 对象 自己构造 Parcel 调 transact

public String getAndroidId(Context context) {
    try {
        // 第一步 拿到 ActivityThread 的当前实例
        // ActivityThread 是 App 进程的主线程管理类 每个 App 进程一个
        // currentActivityThread 是静态方法 返回当前进程的 ActivityThread 对象
        Class<?> activityThreadClass = Class.forName("android.app.ActivityThread");
        Method currentActivityThreadMethod = activityThreadClass.getMethod("currentActivityThread");
        Object currentActivityThread = currentActivityThreadMethod.invoke(null);

        // 第二步 调 acquireProvider 拿到 settings 这个 ContentProvider 对象
        // 参数1 context
        // 参数2 "settings" 是 authority 名
        // 参数3 0 是用户 ID 通常主用户是 0
        // 参数4 true 表示 stable 模式
        // 这一步等价于 ContentResolver 内部找 Provider 的过程
        Method acquireProviderMethod = activityThreadClass.getMethod(
            "acquireProvider", Context.class, String.class, int.class, boolean.class);
        Object provider = acquireProviderMethod.invoke(
            currentActivityThread, context, "settings", 0, true);

        // 第三步 从 provider 里反射拿 mRemote 字段
        // mRemote 就是 IContentProvider 持有的 Binder 对象
        // 它才是真正的跨进程代理 指向 system_server 的 SettingsProvider
        // ContentResolver 内部也是通过这个 mRemote 发请求的
        Class<?> iContentProviderClass = Class.forName("android.content.IContentProvider");
        Field mRemoteField = provider.getClass().getDeclaredField("mRemote");
        mRemoteField.setAccessible(true);
        IBinder binder = (IBinder) mRemoteField.get(provider);

        // 第四步 构造 Parcel 准备发请求
        // Parcel 是 Binder 通信的数据容器 按顺序读写
        Parcel data = Parcel.obtain();

        // writeInterfaceToken 是 Binder 协议要求的第一步
        // 声明接口名 不写服务端会拒绝
        data.writeInterfaceToken("android.content.IContentProvider");

        // 下面按 Android 版本写不同字段
        // IContentProvider.call 的签名在 Android 10 11 12 各改过一次
        // 不按版本写 服务端解析 Parcel 会错位

        if (android.os.Build.VERSION.SDK_INT >= android.os.Build.VERSION_CODES.S) {
            // Android 12 API 31 及以上
            // 先写 AttributionSource
            context.getAttributionSource().writeToParcel(data, 0);
            data.writeString("settings");     // authority
            data.writeString("GET_secure");   // method
            data.writeString("android_id");   // stringArg
            data.writeBundle(Bundle.EMPTY);   // extras
        } else if (android.os.Build.VERSION.SDK_INT == android.os.Build.VERSION_CODES.R) {
            // Android 11 API 30
            data.writeString(context.getPackageName());
            data.writeString(null);           // featureId 这个版本有
            data.writeString("settings");     // authority
            data.writeString("GET_secure");   // method
            data.writeString("android_id");   // stringArg
            data.writeBundle(Bundle.EMPTY);
        } else if (android.os.Build.VERSION.SDK_INT == android.os.Build.VERSION_CODES.Q) {
            // Android 10 API 29
            data.writeString(context.getPackageName());
            data.writeString("settings");     // authority
            data.writeString("GET_secure");   // method
            data.writeString("android_id");   // stringArg
            data.writeBundle(Bundle.EMPTY);
        } else {
            // Android 9 及以下
            data.writeString(context.getPackageName());
            data.writeString("GET_secure");   // method
            data.writeString("android_id");   // stringArg
            data.writeBundle(Bundle.EMPTY);
        }

        // 第五步 准备 reply Parcel 调 transact
        Parcel reply = Parcel.obtain();

        // CALL_TRANSACTION 是 IContentProvider 接口里 call 方法的 transaction code
        // 每个 Binder 方法有一个整数编号 transact 时传这个编号
        // 服务端 onTransact 里按编号分发
        binder.transact(
            (int) iContentProviderClass.getDeclaredField("CALL_TRANSACTION").get(null),
            data, reply, 0);

        // 第六步 读回复
        // 先读异常 如果服务端抛了异常 这里会重新抛出
        reply.readException();

        // 再读 Bundle 从里面取 value
        Bundle bundle = reply.readBundle();
        reply.recycle();
        data.recycle();
        return bundle.getString("value");
    } catch (Exception e) {
        e.printStackTrace();
        return null;
    }
}
```

```text
// 调用链层次
ContentResolver.call(...)
  │
  │ 内部解析 Uri 拿到 authority 比如 "settings"
  │ 根据 authority 找到对应的 IContentProvider 代理
  ▼
IContentProvider 代理  // 接口是 IContentProvider 实现类是它的 Proxy
  │
  │ 这个代理内部持有 IBinder 对象
  │ IBinder 的实际类型是 BinderProxy
  ▼
BinderProxy.transact(...)
  │
  │ native 方法 通过 JNI 进 libbinder
  ▼
IPCThreadState::transact(...)
  │
  │ ioctl 进内核
  ▼
Binder 驱动
```

#### SERIAL

`Serial` 设备序列号 全称 `Device Serial Number` 厂商在出厂时写入设备的硬件标识，现在基本不使用了

```java
// 不同平台路径不同

// API 层获取路径

// 路径一 Build.SERIAL 静态字段
// Android 8.0 API 26 之前 直接返回真实序列号
// Android 8.0 之后 返回 "UNKNOWN" 除非有 READ_PHONE_STATE
String serial = Build.SERIAL;
CLog.i("Build.SERIAL -> " + serial);

// 路径二 Build.getSerial() 方法
// Android 8.0 API 26 引入
// 需要 READ_PHONE_STATE 权限
// Android 10 API 29 起需要 READ_PRIVILEGED_PHONE_STATE
// 普通第三方 App 无法申请这个权限
try {
    String serial = Build.getSerial();
    CLog.i("Build.getSerial -> " + serial);
} catch (SecurityException e) {
    // 权限不足 抛异常
    CLog.e("Build.getSerial 失败: " + e.getMessage());
}

// 路径三 Settings.Secure.getString(..., "serial")
// 早期 Android 有这条路径
// Android 8.0 之后基本废弃 返回 null 或 UNKNOWN
String serial = Settings.Secure.getString(
    context.getContentResolver(),
    "serial"
);
CLog.i("Settings.Secure serial -> " + serial);
```

```java
// 蓝牙相关
// 两个字段 蓝牙 MAC 地址 和 蓝牙名称
// 早期存在 Settings.Secure 表里
// Android 10 API 29 之后普通 App 拿不到真实 MAC

// 读法一 通过 BluetoothAdapter
```

```java

//       国际移动设备识别码

//       国际移动用户识别码

//       集成电路卡识别码
//       标识 SIM 卡本身
```

```java

// 标识谁       设备硬件            用户身份            SIM 卡本身
// 存在哪       基带或存储芯片      SIM 卡             SIM 卡
// 谁分配       设备厂商            运营商             卡厂
// 位数         15 位               最多 15 位         19 到 20 位
// 换手机        变                  不变               不变
// 换 SIM 卡    不变                变                 变
// 恢复出厂      不变                不变               不变
// 分类         不变项              缓变项             缓变项
```

```java
// sourceDir 里的随机串是什么

// 路径结构
// /data/app/~~[随机串A]/[包名]-[随机串B]/base.apk

// 两个随机串
// 随机串A 是上层目录的随机名
// 随机串B 是 APK 所在目录的随机名
// 都是 base64 编码的 16 字节随机数

// 生成代码在 PackageManagerService 里
// 方法名 getNextCodePath
// 用 SecureRandom 生成 16 字节
// base64 编码后拼进路径

// 为什么 Android 要这么做
// 早期 Android 里 APK 路径是固定的 /data/app/包名-1/base.apk
// 这样有安全问题
//   攻击者可以预测路径 提前放恶意文件
//   或者通过路径猜测哪些 App 已安装
// Android 8.0 之后改成随机路径
// 每次安装都重新生成
// 提高安全性和隐私性
```

```java
// 生成逻辑简化

// PackageManagerService 内部
public static File getNextCodePath(File targetDir, String packageName) {
    SecureRandom random = new SecureRandom();
    byte[] bytes = new byte[16];

    // 生成上层目录的随机名
    File firstLevelDir;
    do {
        random.nextBytes(bytes);
        String firstLevelDirName = "~~" + Base64.encodeToString(
            bytes, Base64.URL_SAFE | Base64.NO_WRAP);
        firstLevelDir = new File(targetDir, firstLevelDirName);
    } while (firstLevelDir.exists());

    // 生成包目录的随机名
    random.nextBytes(bytes);
    String dirName = packageName + "-" + Base64.encodeToString(
        bytes, Base64.URL_SAFE | Base64.NO_WRAP);

    return new File(firstLevelDir, dirName);
}

// 最终路径形如
// /data/app/~~AHYpV_2lR-Fkh_r6agIhA==/com.example.app-YU8zCBpdRtzAnWanZy2nfw==/base.apk
```

```c
// Netlink 是 Linux 内核提供的一种 IPC 机制
// 用于用户态和内核态通信
// ip ifconfig 这些命令底层就是走 Netlink

// 第一步 创建 Netlink socket

// NETLINK_ROUTE 表示要和内核的网络子系统对话

// 第二步 发 RTM_GETLINK 请求 要所有网络接口信息
struct {
    struct nlmsghdr hdr;
    struct rtgenmsg msg;
} request;
memset(&request, 0, sizeof(request));
request.hdr.nlmsg_flags = NLM_F_DUMP | NLM_F_REQUEST;
request.hdr.nlmsg_type = RTM_GETLINK;
request.hdr.nlmsg_len = sizeof(request);
request.msg.rtgen_family = AF_UNSPEC;
send(fd, &request, sizeof(request), 0);

// 第三步 收内核返回
char buf[8192];
recv(fd, buf, sizeof(buf), 0);

// 第四步 解析返回 拿到接口名和 MAC
```

### Soc

```java
// SoC 序列号
// SoC 全称 System on Chip
// 中文 系统级芯片
// 把 CPU GPU 基带 内存控制器 等集成在一块芯片上
// 手机的主芯片就是 SoC
// 比如骁龙的 8 Gen 2 天玑 9200 麒麟 9000

// 但普通 App 读不到 因为 SELinux 限制
// 只有 root 或系统进程能读

// 分类 不变项
// 唯一性高 稳定性高
// 但可获得性差

// 原因一 很多设备这个文件不存在
//   不同厂商不同平台 路径不同
//   有的设备根本没有暴露 serial_number

// 原因二 存在也读不到
//   /sys/devices/soc0/serial_number
//   权限通常是 root 或者 system
//   普通 App 打开会 Permission denied

// 原因三 SELinux 拦截
//   即使文件权限放开了
//   SELinux 策略也不允许 untrusted_app 读
//   会抛 avc:denied

// 所以普通未 root 设备上
// 这个字段基本采集不到
// 只有 root 设备或系统应用能读

// SoC 序列号是芯片出厂时烧录的唯一标识
// 存在 /sys/devices/soc0/serial_number
// 恢复出厂不变 重启不变 用户改不了
// 分类 不变项
// 但普通 App 读不到 需要 root 或系统权限
// 改机方要改必须写内核模块 成本高
// 所以如果能拿到 可信度比 IMEI 更高
```

```java
            CLog.i("IPv6 -> " + addr.getHostAddress());
        }
    }
}
```

### 系统文件信息

```java
// 系统文件信息
// 通过 stat 和 statfs 两个系统调用
// 读文件和文件系统的元数据
// 元数据由内核维护
// App 拿到的是内核返回的结果
// Java 层 Hook 拦不住

#include <sys/stat.h>

struct stat64 buff = {0};
stat64("/system/build.prop", &buff);

// 读完之后 buff 里就有这个文件的所有元数据
// buff.st_ino     文件的 inode 号
// buff.st_dev     文件在哪个设备上
// buff.st_size    文件多大
// buff.st_mode    文件权限
// buff.st_mtime   文件内容最后修改时间
// buff.st_ctime   文件元数据最后变更时间
// buff.st_atime   文件最后被访问时间
```

```java
// inode 是什么
// 文件系统给每个文件分配一个编号
// 叫 inode 号
// 同一个文件系统内 inode 号唯一
// 不同文件系统可以重复

// 类比
// 图书馆每本书有一个编号
// 1 号书 2 号书 3 号书
// 这个编号就是 inode
// inode 号告诉内核这个文件在磁盘哪个位置
// 它的元数据存在哪里
```

```java
//同样的，我们可以读文件系统的信息

#include <sys/vfs.h>
#include <sys/statfs.h>

struct statfs64 buff = {0};
statfs64("/data", &buff);

// 读完之后 buff 里有 /data 这个文件系统的信息
// buff.f_type     文件系统类型 ext4 还是 f2fs
// buff.f_bsize    块大小 通常 4096 字节
// buff.f_blocks   总共有多少个块
// buff.f_bfree    空闲多少块
// buff.f_files    总共有多少个 inode
// buff.f_ffree    空闲多少个 inode
// buff.f_fsid     这个文件系统的唯一 ID
```

```java
// 采集思路
// 采集几十到上百个关键文件或目录的 stat
// 加上几十个关键分区的 statfs
// 组成一个矩阵 上传服务端
// 服务端比对

// 关键路径举例
// /system/build.prop
// /system/framework/framework-res.apk
// /data
// /system
// /vendor
// /data/app
// /data/dalvik-cache

// 每个路径读到的字段
// inode
// dev
// mtime
// ctime

// 组合起来唯一性很高
// 因为不同设备的文件系统布局 编译时间 不同
```

```java
// 为什么难 Hook

// 系统服务层
//   我通过 Binder 调 system_server
//   改机方在 Java 层 Hook 就改掉了
//   Frida 一行代码

// 内核层
//   我通过 syscall 直接向内核要数据
//   数据从内核返回到用户空间
//   Java 层 Hook 拦不住
//   改机方要改必须
//     内核模块
//     或者 Hook libc 层
//     或者 Hook syscall 指令
//   成本比改 Java 层高得多

// 系统文件信息通过 stat 和 statfs 读
// stat 读文件元数据 inode dev mtime ctime 等
// statfs 读文件系统元数据 f_fsid f_blocks 等
// 但是Magisk 可以用 namespace 挂假文件骗过 stat
// 可以采取跨 namespace 对比
```

```java
// 系统属性 System Properties
// 可以理解成一个全局的 key-value 表
// 系统启动 硬件配置 调试开关 都往里塞
// getprop 命令读的就是它
// SystemProperties.get 读的也是它
```

```java
// 怎么读
// getprop                    列出所有属性
// getprop ro.build.version.sdk   读单个属性

// Java 层
String sdk = SystemProperties.get("ro.build.version.sdk");
CLog.i("sdk -> " + sdk);

//Native层

#include <sys/system_properties.h>
#include <stdio.h>

void read_prop(const char *name) {
    char value[PROP_VALUE_MAX];
    int len = __system_property_get(name, value);
    if (len > 0) {
        printf("%s = %s\n", name, value);
    } else {
        printf("%s 读取失败或不存在\n", name);
    }
}

int main() {
    read_prop("ro.build.version.sdk");
    read_prop("ro.product.model");
    read_prop("ro.boot.verifiedbootstate");
    return 0;
}

// 但 SystemProperties 是隐藏 API
// Android 9 之后反射受限
// 需要绕过隐藏 API 限制

// 属性分类
// 按前缀分

// ro. 开头    只读属性 read-only
//             启动时设置 之后不能改
//             比如 ro.build.fingerprint
//             比如 ro.product.model

// persist. 开头  持久化属性
//                可以改 会存到 /data/property/
//                重启后还在

// sys. 开头    系统属性
//              可以改 重启后丢失

// debug. 开头  调试属性

// 其他        普通属性

// ro. 属性 本意是只读
// 但 root 下用 Magisk 的 resetprop 可以改
// 一行命令
// resetprop ro.build.fingerprint "伪造的值"

// resetprop 原理
// 直接操作属性服务的内存区域
// 绕过 SELinux 限制
// 成本低

// 从应用层 Hook
// Frida Hook SystemProperties.get
// 成本也低

// 所以系统属性抗篡改能力弱
// 改机方最爱改的就是 ro.build.fingerprint 这些
```

```java
// 分类

// ro.build.fingerprint  缓变项  OTA 才变  但容易被改
// ro.product.model      不变项  但容易被改
// ro.serialno           不变项  但容易被改
// ro.boot.verifiedbootstate  缓变项  解锁 BL 后变 orange  容易被改

// 系统属性整体上
// 稳定性看具体 key
// 唯一性看具体 key
// 可获得性高 普通 App 能读大部分
```

```java
// 设备指纹里怎么用

// 用途一 采集构建指纹
//   ro.build.fingerprint
//   ro.product.model
//   ro.product.brand
//   组合起来描述设备轮廓

// 用途二 判断环境
//   ro.boot.verifiedbootstate
//   green 正常 orange 解锁
//   ro.debuggable
//   1 表示可调试

// 用途三 交叉验证
//   ro.product.model 说这是小米
//   但 ro.product.brand 说是华为
//   两者矛盾 可能被改机

// 用途四 结合其他字段
//   系统属性 + 文件系统信息
//   属性说 Android 13
//   但某些文件 mtime 是 Android 12 的编译时间
//   矛盾

// 设备指纹里常采集构建指纹 型号 品牌 启动状态
// 必须和其他字段交叉验证 单看不可信

// getprop 命令的完整链路

// 你敲 getprop ro.build.version.sdk

// 1 shell 解析命令 找到 /system/bin/getprop
// 2 启动 getprop 进程
// 3 getprop 调 __system_property_get("ro.build.version.sdk", value)
// 4 __system_property_get 打开 /dev/__properties__/u:object_r:system_prop:s0
// 5 mmap 映射到进程空间
// 6 在 prop_bt 树里查找 ro.build.version.sdk
// 7 找到对应的 prop_info 读出 value
// 8 返回给 getprop
// 9 getprop 打印到 stdout
// 10 你看到 "33"

//   方式一 Java 层 SystemProperties.get
//   方式二 Native 层 __system_property_get
//   方式三 直接 mmap /dev/__properties__ 自己解析
//   三条路径读同一个属性
//   改机方 Hook 了 Java 层 方式一拿假值
//   方式二方式三可能拿真值
//   多路径交叉能发现 Hook
```

## DRM

```java
// DRM 数字版权管理
// 全称 Digital Rights Management
// 让内容只能被授权的人看 不能被随意复制传播
// 核心是加密 密钥要安全存储

// 为什么需要 DRM
// 视频网站花大价钱买电影版权
// 用户付费才能看
// 如果用户能随便下载随便拷贝
// 就没人付费了 版权方也不干了
// 所以需要 DRM 保证能看不能拷

// TEE 可信执行环境
// 全称 Trusted Execution Environment
// 手机主芯片上的一块安全区域

// TEE 里存
// 加密密钥
// 指纹模板
// 支付凭证
// 人脸数据
// DRM 密钥
// DRM ID
// 这些东西 Android 读不到明文
// 只能通过特定接口向 TEE 请求
// TEE 处理后返回结果
```

```java
// Widevine 是 Google 的 DRM 方案
// 它为每台设备在 TEE 里生成一个唯一 ID
// 叫 DRM ID 或 Widevine ID
// 全称 PROPERTY_DEVICE_UNIQUE_ID

// 特点
// 在 TEE 里生成
// 存在 TEE 里
// Android 系统只能读不能改
```

```java
// Java 层怎么读 DRM ID

import android.media.MediaDrm;
import java.util.UUID;

// 第一步 构造 Widevine 的 UUID
// 这个 UUID 是固定的 Widevine 标识
UUID wideVineUuid = new UUID(
    -0x121074568629b532L,
    -0x5c37d8232ae2de13L
);

// 第二步 创建 MediaDrm 实例
MediaDrm wvDrm = new MediaDrm(wideVineUuid);

// 第三步 读 PROPERTY_DEVICE_UNIQUE_ID
byte[] wideVineId = wvDrm.getPropertyByteArray(
    MediaDrm.PROPERTY_DEVICE_UNIQUE_ID
);

// 第四步 转成十六进制或 Base64 字符串
String idHex = bytesToHex(wideVineId);
CLog.i("drm id -> " + idHex);

// 第五步 释放
wvDrm.close();

// 返回的 byte 数组通常 16 到 32 字节
// 转成十六进制后大概长这样
// 1a2b3c4d5e6f7890a1b2c3d4e5f67890
```

```c
// Native 层也能读
// 用 NDK 的 MediaDrm API

#include <media/NdkMediaDrm.h>

// Widevine UUID
const uint8_t uuid[] = {
    0xed, 0xef, 0x8b, 0xa9, 0x79, 0xd6, 0x4a, 0xce,
    0xa3, 0xc8, 0x27, 0xdc, 0xd5, 0x1d, 0x21, 0xed
};

// 创建 MediaDrm 实例
AMediaDrm *mediaDrm = AMediaDrm_createByUUID(uuid);

// 读 deviceUniqueId
AMediaDrmByteArray mediaDrmByteArray;
AMediaDrm_getPropertyByteArray(
    mediaDrm,
    PROPERTY_DEVICE_UNIQUE_ID,
    &mediaDrmByteArray
);

// mediaDrmByteArray.ptr 是数据指针
// mediaDrmByteArray.length 是长度
// 转成 Base64 或十六进制上报

// 释放
AMediaDrm_delete(mediaDrm);

// 读 DRM ID 不需要任何权限
// 普通 App 就能调 MediaDrm
// 这是它比 IMEI 好的地方之一

// 它是应用级的 不是设备级的
// 较新的 Android 系统上
// 同一台设备 不同包名的 App
// 读到的 DRM ID 不同
// 所以它不能用来跨应用追踪同一台设备

// 不是所有设备都支持
// 低端机 特殊 ROM 可能没有 Widevine
// 读不到 DRM ID
// 极少数情况可能返回空值或崩溃

// 部分定制系统会限制
// 像 GrapheneOS 这类注重隐私的 ROM
// 可能提供开关禁用硬件级 DRM ID
// 转而用软件生成的随机 ID
```

```java

// 理论上可以 Hook MediaDrm.getPropertyByteArray
// 改返回值
// 但 DRM ID 在 TEE 里生成
// Hook 只是改应用层看到的值
// 底层真实值没变
// 有些 App 会交叉验证

// 所以 DRM ID 的抗篡改能力很强
// 是设备指纹里可信度最高的字段之一
```

```java
            → 返回
```
